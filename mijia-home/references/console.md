# 米家极客版 Web 控制台自动化

> 配套：规则 JSON/节点见 `references/rule-kit.md`；.bak 打包/解包见 `references/backup.md`。
> 入门用户请先读 `references/beginner.md`。

使用当前 AI 环境实际提供的浏览器/电脑工具，并先阅读该工具的操作说明；不要假设 Playwright MCP 或其他特定工具已安装。若无法安全读取或操作页面，说明限制并给用户手动步骤。

**控制台地址**：使用用户提供或当前已打开的地址；不要自行假定 IP、端口或网关型号。

---

## 写入网关的两条路

- **首选 MijiaFlow**（已配置时）：按单条规则或单个变量写入（`set_graph`、`create_variable` 等）。流程固定为：`mijia_read` 读现状 → `mijia_plan_change` 出差异和一次性确认语 → `mijia_create_backup` → 用户亲自发确认语 → `mijia_apply_change` 回读核对；出错用 `mijia_rollback`。不会整体覆盖其他规则。
- **备用：控制台导入 .bak**：整体覆盖全部规则和变量，只在没有 MijiaFlow 时使用。导入前必须重新导出一次，确认导出后网关没被改过，再把差异给用户看。

两条路都只在用户明确要求写入时才走。

---

## 登录（唯一人机协作点）

首页要求 **6 位数字登录码**——由用户从米家 App 获取并在登录页自行输入。将其作为短时授权码处理；不要索要或复述到聊天里。若页面已登录，避免硬刷新。

🚨 **任何硬刷新都会登出**，登录态在会话内保持（见下方 SPA 导航避坑）。

## 收集 did 与设备名称的映射

### 首选：MijiaFlow 本地 MCP

如果当前 Agent 已配置并能调用 **MijiaFlow**，优先走它的只读路径。它经本机回环配对后调用网关的 `getDevList`，单个网关响应同时返回 `did`、设备名、房间、型号和在线状态，因而可直接作为 `did ↔ 名称 ↔ 房间` 的确认依据。

1. `mijia_probe(baseUrl)`：确认网关地址和协议；先记录只读/可写能力，不因后续工作需要而绕过不兼容保护。
2. `mijia_begin_session(baseUrl)`：仅打开一次 `127.0.0.1` 配对页。用户自行输入 6 位动态码；不要把动态码、配对 URL 或会话资料写进聊天、日志或台账。
3. `mijia_session_status()` 返回 `ready` 后，调用 `mijia_read(resource="devices", filters={})`。将原始结果保存为 JSON，并保留采集时间和网关地址。
4. 用 `scripts/device_registry.py "备份.bak" --mijiaflow-devices "devices.json" --out "设备台账.json"` 合并实时映射与备份中的规则引用。
5. MijiaFlow 不返回用户自定义的每键显示名。按键名称仍要从已渲染的规则卡、同一设备的设置页或用户确认中采集；没有证据则保持 `未核对`。

不要假定某个 npm 包或 MCP 配置已经可用。先成功执行 `mijia_probe`，再把它作为本次会话的可信读取源。

### 备份和画布兜底

导出的 `.bak` 提供已出现在规则中的 `did`，设备列表和画布卡片提供名称、房间和按键。处理现有规则时，按同一节点完成映射：解包备份找到节点 `id` 与 `props.did`，再在画布中读取该节点显示的设备名、房间及所选事件/动作，写入设备台账。这个对应关系可验证；不要按设备列表顺序或同型号设备猜测。

对从未出现在规则中的设备，不能从设备列表的排序、名称或型号反推出 `did`。`did` 在设备列表的 WebSocket 数据中，通常不在 DOM 中；若当前 Agent 没有可靠的 WebSocket 读取能力，采用下面的「台账采集规则」建立可审计映射。

### 从零建立设备台账（没有已有自动化）

只有在用户明确要求采集台账时，才在控制台创建一条临时规则 `_台账采集`。这是一次配置变更，但规则保持**停用**，且不连接任何节点，因此不会向设备发出动作。

1. 先从「设备列表」收集每台设备的可见名称、房间、品类、型号和通道；保留截图或同等可验证的页面记录。
2. 新建 `_台账采集`，显式保持 `enable: false`。对每个要纳入自动化的设备和每个独立按键/通道，拖入一个已选中该设备的事件、状态或操作卡片；不要拉线，不要启用，也不要设置会在保存时执行的动作。
3. 保存后导出完整 `.bak`。解包可从每张卡片的 `props.did` 和 `cfg.urn` 读取真实设备地址；画布卡片的名称、房间、通道是其唯一允许的显示名来源。
4. 用 `scripts/device_registry.py` 生成台账，并只把同一张画布卡片已显示的信息写为 `confirmed`。没有可选卡片或无法唯一核对的设备保持 `unresolved`，不为它生成规则。
5. 留存「采集前完整备份」和「含台账采集规则的完整备份」。台账确认后，可在用户要求下删除临时规则；已确认的台账 JSON 仍作为后续规则的寻址依据。

## 自验证闭环（推荐）

生成规则 JSON → 本地校验 → 保留最新完整备份 → 仅在用户明确要求导入时上传（覆盖）→ **三重验证**：

1. **画布结构自检**：进编辑器看规则渲染成的卡片，逐卡比对设计确认节点语义无误；新规则默认停用。
2. **读全局变量值**：变量驱动型逻辑可注入/读取全局变量确认。
3. 🔑 **执行日志/回放**：编辑器底部「文档」图标→选时间范围→点记录在画布上逐节点回放。日志可证明规则链路如何运行；不要为测试而触发有现实影响的设备。结构校验通过不等于行为验证通过。

🔑 **调试期缩短长延时，上线前恢复**：长延时先临时改秒级（如 20s）便于快速触发验证，通过后恢复生产值重导。

## 🚨 导入排错与避坑

- **校验时机**：节点校验在「上传文件」**选中文件那一刻**就跑，不是点「确定」时。判据——选文件后「确定」**保持可点**=校验通过；若「确定」变 **loading 永不结束**=校验失败。
- **定位违规节点**：失败时查看浏览器控制台报错，搜索 `Uncaught ... Invalid node parameter:<节点id>,<原因>`。
- **失败会污染全局状态**：一次校验失败后「确定」**永久 loading**，后续重开的导入弹窗一打开就是 loading——此时任何重试都无效，看到的报错都是旧的。
- ⚠️ **「导入成功」≠「编辑器能渲染」**：枚举属性用标量而非 `include`+数组（见 references/rule-kit.md）会让编辑器整页白屏崩溃（控制台见 `Uncaught TypeError`，如 `r.includes is not a function`）。崩溃后只能**硬刷新**（=登出重登）。⟹ 导入后**务必进编辑器确认能正常渲染**。
- **必须硬刷新才能恢复**：但硬刷新=登出。⟹ **代价高，别靠反复重试**：改完一版先本地审计（用 mijia_rule_kit 的 `validate`），力求**一次导对**。

## 🚨 SPA 导航避坑

- 导航到**相同 hash**= 空操作，脏状态清不掉
- 导航到**不同 hash**= React 白屏，hash 路由救不回，只能硬刷新
- 导航到**无 hash URL**= 硬刷新 = **登出**（需用户重取码）
- ✅ 正确做法：用页面内元素点击切换视图；只有清污染/登出时才有意硬刷新
